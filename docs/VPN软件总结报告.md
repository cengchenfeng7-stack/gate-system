## 一、为什么自己开发——自主可控 vs 依赖他人软件

### 1.1 核心观点

**使用别人的软件，出了问题你只能抱怨；自己开发，出了问题你只会想办法修。**

这不是技术问题，是掌控力的问题。当你把 VPN 这种"网络命脉"交给第三方软件时，你实际上是在赌它的开发者不会：
- 留暗门（后门代码、隐藏数据通道）
- 埋暗坑（默认配置漏洞、隐私泄露）
- 突然停更（项目abandon，安全漏洞无人修）
- 植入数据收集（遥测、行为追踪、节点劫持）

而自己开发，这些问题根本不存在——因为源码在你手里，每一行代码都经过你的审查。

### 1.2 用户心声（原话）

> "现在的人都是：使用没问题的时候还好会夸。使用感觉一般了就会考虑换工具。使用感觉很差了不但换工具还进行人身攻击和差评。我要自己开发的话，出了问题修起来也没有怨言，只会说哎呀网络这边没有优化好或者反代没做好或者网关啥的没做好，然后找人帮忙去进行加功能或者进行大改。"

**这段话道出了一个残酷现实**：第三方软件的用户，出了问题只能被动等待、抱怨、甚至被开发者无视。而自主开发者，出了问题有明确的修复路径——查日志、定位问题、改代码、验证。

### 1.3 暗门/暗坑的多重风险

| 风险类型 | 具体表现 | 后果 |
|---|---|---|
| 后门代码 | 隐藏的管理员接口、远程配置下发 | 节点被劫持、流量被监控 |
| 暗坑配置 | 默认开启遥测、日志上传 | 隐私泄露、行为追踪 |
| 停更风险 | 项目 abandon、安全漏洞无人修 | 暴露在攻击者面前 |
| 供应链攻击 | 依赖库被污染、构建系统被入侵 | 所有用户受影响 |
| 数据外发 | 节点信息、配置被上报 | 私有部署暴露 |

**自主开发的本质**：不是重复造轮子，而是把"网络命脉"掌握在自己手里。

```
│  └─ 生成产物发布到 Pages                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐

│  │   SSTP over TLS + PPP 拨号 + 出口情报                      │
│  └─ vless (worker.js)                                        │

└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   GitHub Pages                                │
│  data.json + index.html 面板 + 八分组节点列表                  │
└─────────────────────────────────────────────────────────────┘
                              │
                ┌─────────────┴─────────────┐
                ▼                           ▼
┌──────────────────────┐    ┌──────────────────────┐
│ A 端 (Clash Verge)   │    │ B 端 (vpn_dial.py)   │
│ VLESS 订阅            │    │ OpenVPN 系统级拨号    │
│ 规则代理              │    │ 全局流量走 VPN        │
└──────────────────────┘    └──────────────────────┘
```

### 2.2 数据流

1. **抓取**：vpngate.py 每 30 分钟抓 VPN Gate feed（官方 API + 镜像回退）
2. **检测**：调 checker Worker 做 SSTP over TLS + PPP 拨号 + 出口情报
3. **评级**：四场景判定（客服/游戏/下载/AI）+ 稳定性分层
4. **发布**：生成 data.json + 八分组节点列表 → GitHub Pages
5. **消费**：A 端 Clash Verge 导入 VLESS 订阅；B 端 vpn_dial.py 拨号 OpenVPN

### 2.3 八分组面板

| 分组 | 条件 | 用途 |
|---|---|---|
| 日常组 | 所有可用节点 | 默认视图 |
| 下载组 | speed_ready | 高带宽 + 稳定 |
| 游戏组 | game_ready | 低延迟 + 低抖动 |
| 客服组 | support_ready | 干净 IP + 住宅 + 长在线 |
| AI 组 | ai_ready | 干净 IP + 长在线 |
| 机房组 | is_datacenter_node | 机房节点单独管理 |
| 养鱼组 | fish_ready | 稳定但暂不够格进四场景 |
| 观察组 | 不稳定但可用 | 波动中待观察 |

## 三、ECH 兼容性案例——协议兼容性适配和协议更新速度

### 3.1 问题复现

**现象**：worker 开启 ECH 后，Hiddify 导入节点链接/自适应/Base64 格式报错 `[V2rayParser] invalid sing-box config: parse outbound[muchen] error: invalid ECH configs pem`。

**根因**：edgetunnel 代码把 ECH 配置塞进了节点链接的 URL 查询参数（`&ech=...`）和 SingBox 配置的 TLS 字段（`query_server_name`）。`query_server_name` 是 sing-box **1.13.0+** 的新字段，Hiddify 当前版本的 sing-box 太旧不认识，解析到就报 `invalid ECH configs pem`。

### 3.2 技术本质

**ECH（Encrypted Client Hello）是 TLS 1.3 的扩展**，通过 DNS HTTPS 记录分发 ECH 配置，在 TLS 握手中加密 SNI（服务器名称指示）。

**兼容性困境**：
- ECH 是新技术，客户端/转换后端/代理工具的支持参差不齐
- 新版 sing-box（1.13.0+）用 `query_server_name` 字段
- 旧版 sing-box 不认识这个字段，直接报错
- 第三方转换后端（SUBAPI）大多不支持 ECH 字段透传

### 3.3 协议更新速度的挑战

| 层面 | 问题 | 影响 |
|---|---|---|
| 协议层 | ECH 标准仍在演进，客户端实现不统一 | 同一配置在不同客户端表现不一致 |
| 客户端层 | sing-box/clash mihomo 内核更新快，但用户版本参差 | 新版字段旧版不认识 |
| 转换层 | 第三方 SUBAPI 大多不支持 ECH 字段 | 转换后配置丢失或报错 |
| 工具层 | edgetunnel 等生成器追求新特性，但忽略兼容性 | 生成的配置在某些客户端不可用 |

### 3.4 解决方案

**最终方案**：不在节点链接和 SingBox 配置里显式嵌入 ECH 字段，让 ECH 通过 DNS HTTPS 记录在 TLS 握手时自动获取。

- 新版客户端（sing-box 1.13.0+、Clash Verge Rev）：自动通过 DNS HTTPS 记录获取 ECH 配置
- 旧版客户端（Hiddify 当前版本）：不支持 ECH 但不会报错，正常工作
- 所有协议格式（节点链接/自适应/Base64/Clash/SingBox）：全部兼容

### 3.5 教训

**协议兼容性是 VPN 系统的核心挑战**：
- 新协议特性（如 ECH）的采用速度不一，客户端/服务端/转换层的支持存在时间差
- 显式嵌入新字段会导致旧客户端报错
- 最佳实践：让新特性通过标准机制（如 DNS HTTPS 记录）自动工作，而不是显式嵌入配置

## 四、对 VPN 软件的看法——自主开发的价值、当前局限、下一步方向

### 4.1 自主开发的价值

| 维度 | 使用第三方软件 | 自主开发 |
|---|---|---|
| 掌控力 | 黑盒，出了问题只能等修复 | 白盒，出了问题知道改哪里 |
| 信任 | 需要信任开发者不留暗门 | 源码审查，每一行都经过验证 |
| 定制化 | 受限于软件提供的选项 | 完全定制，想怎么改就怎么行 |
| 响应速度 | 等开发者排期 | 自己控制优先级 |
| 学习价值 | 只会用，不会造 | 从使用到创造，技术能力跃升 |

**用户心声**：
> "我要自己开发的话，出了问题修起来也没有怨言，只会说哎呀网络这边没有优化好或者反代没做好或者网关啥的没做好，然后找人帮忙去进行加功能或者进行大改。"

**本质**：自主开发把"被动等待"变成"主动修复"，把"信任他人"变成"信任自己"。

### 4.2 当前系统的局限

| 局限 | 具体表现 | 影响 |
|---|---|---|
| SSTP 延迟高 | 2000-9000ms，远超四场景阈值 | 客服/游戏/AI 场景永远 0 节点 |
| 协议老旧 | SSTP 是 Windows 原生协议，但性能差 | 高延迟场景无法使用 |
| 网络依赖 | 用户的网络到 vpngate.net/GitHub 不通 | B 端 feed 拉取失败 |
| 节点池小 | VPN Gate 官方只有约 100 个节点 | 扩展空间有限 |
| 客户端缺失 | 没有自己的 VPN 客户端软件 | 依赖 OpenVPN/Hiddify 等第三方工具 |

### 4.3 下一步方向

**核心目标**：开发自己的 VPN 客户端软件，实现完全自主可控。

**技术路线**：
1. **协议升级**：从 SSTP 升级到 VLESS/Trojan（延迟 100-300ms）
2. **客户端开发**：基于 sing-box/mihomo 内核，开发自己的 VPN 客户端
3. **配置生成**：优化 gen_client_config.py，生成完全兼容的配置
4. **节点管理**：完善历史缓存 + 养鱼池 + 观察组的三级流转机制
5. **跨平台**：支持 Windows/macOS/Linux/iOS/Android

## 五、意见与观点——对行业现状的看法、对用户心声的回应

### 5.1 对行业现状的看法

**当前 VPN/代理软件行业的三大问题**：

1. **黑盒风险**：大多数商业 VPN 软件不开源，用户无法验证是否存在数据收集、后门、节点劫持。近年来多次爆出免费 VPN 软件出售用户数据的事件。

2. **兼容性碎片化**：协议更新速度快（ECH、Reality、Hysteria2 等），但客户端/服务端/转换层的支持参差不齐，导致"同一配置在不同客户端表现不一致"的混乱局面。

3. **信任危机**：用户出问题时只能依赖开发者，而开发者的响应速度、修复能力、诚信度都无法保证。社交媒体上"用好了夸，用差了骂"的现象普遍。

**自主开发的意义**：不是重复造轮子，而是把"网络命脉"从他人手中拿回来。出了问题有明确的修复路径，不需要等待、不需要抱怨、不需要信任他人。

### 5.2 对用户心声的回应

> "现在的人都是：使用没问题的时候还好会夸。使用感觉一般了就会考虑换工具。使用感觉很差了不但换工具还进行人身攻击和差评。我要自己开发的话，出了问题修起来也没有怨言，只会说哎呀网络这边没有优化好或者反代没做好或者网关啥的没做好，然后找人帮忙去进行加功能或者进行大改。"

**这段话揭示了自主开发的深层价值**：

- **情绪成本**：使用第三方软件出了问题，情绪成本极高（抱怨、差评、人身攻击）。自主开发出了问题，情绪成本极低（"哎呀没优化好"，然后找人帮忙）。

- **掌控感**：自主开发者知道问题的根源在哪，知道怎么修，知道找谁帮忙。第三方软件用户只能等待、只能抱怨。

- **长期价值**：自主开发的技术积累是长期的，每一次修复都是能力的一次提升。第三方软件的使用经验无法积累。

**结论**：自主开发不仅是一种技术选择，更是一种**风险管理策略**——把"依赖他人"的风险转化为"自我修复"的能力。
