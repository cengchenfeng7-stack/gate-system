# 二、最需要修正的五个根本问题

## 1. 第一优先级：重新定义项目的核心目标

你的项目实际上包含三个不同的产品目标。

| 产品方向               | 核心职责                 | 当前建议   |
| ------------------ | -------------------- | ------ |
| 节点检测与评级平台          | 抓取节点、检测出口、统计稳定性、发布分组 | 保留现有主线 |
| Windows 本地 VPN 客户端 | 管理内核、连接、路由、DNS、断线恢复  | 单独立项开发 |
| 节点与网络质量研究平台        | 多来源聚合、长期统计、历史趋势、质量分析 | 作为后续扩展 |

现在的材料已经开始从检测脚本扩展到完整桌面软件。如果不先划分边界，后续很容易出现：GUI 直接操作数据文件、检测模块修改拨号状态、拨号模块自己重新评级、多个模块各自维护一套节点信息的问题。

建议将整个系统拆成两个核心子系统。

## Gate Control Plane

节点检测、质量评级、数据发布

GitHub Actions · Worker · 评级引擎 · 数据发布

版本化数据契约 / JSON API / 本地导入

## Gate Client

Windows 本地连接与运行管理

GUI · 节点选择 · 内核适配器 · 连接状态 · 诊断

### 底层网络引擎

Mihomo / sing-box / OpenVPN 等经过验证的内核

这里有一个重要原则：GUI 不负责判断节点是否合格，GUI 只展示评级结果并向连接管理器发出操作请求。 评级由独立的规则引擎负责，连接管理器负责验证实际连接是否成功。

这能显著降低以后添加新协议、修改界面或者更换内核时的改动范围。

## 2. 第二优先级：重新审视协议路线，而不是继续围绕 SSTP 优化

你的复盘记录中，SSTP 节点延迟约为 2000–9000ms，而游戏、客服和 AI 场景又设置了较低的延迟门槛。这个矛盾值得优先处理。

但需要纠正一个技术概念：VLESS、Trojan 和 SSTP 不能简单理解为三种可以直接互换的 VPN 协议。

VLESS 通常用于代理传输体系；Trojan 是另一类代理协议；SSTP 则是基于 TLS 的 PPP 隧道协议。它们的运行方式、服务端要求、系统接管能力都不同。

另外，VLESS 本身不保证 100–300ms 延迟。实际延迟取决于客户端到入口的网络、入口到出口的网络、服务端负载以及路由质量。

建议调整为以下路线：

阶段 A：完成现有双端验证

保留 OpenVPN B 端用于现有 VPN Gate 节点，保留 Mihomo/VLESS A 端用于规则代理。先验证两端的真实连接、断线恢复和 DNS 行为。

阶段 B：开展独立协议基准测试

在相同网络条件下，比较连接建立时间、往返延迟、抖动、吞吐量、丢包、长连接稳定性和资源占用。不能用单次延迟代替完整的质量评价。

阶段 C：统一连接管理接口

把不同内核包装成统一的连接适配器，支持启动、停止、健康检查、状态查询和错误报告。只有通过验收的协议才进入正式客户端。

这里还有一个比换协议更关键的问题：你的检测系统能否测量真实用户的完整连接路径？

如果 Worker 测到的只是它自身环境中的 SSTP 拨号结果，那么它并不能直接代表你的 Windows 电脑到最终目标网站的实际延迟。两者必须分别记录，不能把远端检测指标直接当作本地连接质量。

## 3. 第三优先级：彻底整理节点数据模型

这是我认为最值得进行实质性重构的部分。

当前设计已经包含 `available`、`watch`、`fish`、`support_ready`、`game_ready` 等字段。但材料中的部分逻辑会从 `available` 推导观察组或养鱼组，同时又允许数据文件直接提供这些分组。若两者发生冲突，就可能产生不一致结果。

建议建立统一、版本化的节点数据模型。

| 数据类别 | 建议包含的字段                        | 作用         |
| ---- | ------------------------------ | ---------- |
| 身份信息 | `node_id`、`source_id`、入口、端口、协议 | 唯一标识节点     |
| 原始测量 | 测量时间、延迟、抖动、带宽、丢包               | 保留实际测量值    |
| 质量结论 | `clean_status`、住宅/机房类型、稳定性     | 表达有证据支持的判断 |
| 资格判断 | 场景资格、失败原因、规则版本                 | 说明为什么入选或淘汰 |
| 历史信息 | 最近测量、失败次数、最后成功时间               | 支持稳定性分析    |
| 连接状态 | 当前是否连接、实际出口、运行内核               | 由本地客户端维护   |

其中有四个规则必须明确。

- 未知不等于合格。 没有测量值时，延迟、抖动、IP 信誉和稳定性都应标为未知，而不是填零。
- 测量值不等于资格结论。 节点是否符合游戏或 AI 场景，应由明确的规则引擎计算。
- 分组不应成为第二套真相。 最好保存测量数据与资格结果，再按规则计算八分组，避免多处重复维护。
- 评级与连接成功必须分开。 节点符合资格不代表当前一定能连接；实际连接失败也不应直接覆盖历史测量记录。

建议为数据增加 `schema_version`、`measured_at`、`source`、`rule_version` 和 `diagnostics`。这样以后修改评级标准时，才能判断某个节点为什么被评为合格，以及旧数据能否继续使用。

## 4. 第四优先级：重写连接状态机，而不是继续堆叠自动重连逻辑

你当前的 B 端设计包含候选节点选择、拨号、掉线检测以及自动切换。但系统级 VPN 的连接管理远比启动一个子进程复杂。

至少需要显式定义以下状态：

DISCONNECTED

未连接，可发起连接

PREPARING

检查配置、内核、驱动和权限

CONNECTING

启动内核，等待真实连接成功

CONNECTED

验证隧道、出口、DNS 和路由

DEGRADED

连接存在，但健康检查未通过

RECONNECTING

断开旧连接并尝试恢复

STOPPING

停止进程、清理资源、恢复必要状态

建议重写或独立实现连接管理器，统一管理状态转换、进程句柄、取消操作、超时、日志和资源清理。

特别要补上这些情况：

- 用户连续点击连接、断开或切换节点时，不允许多个拨号任务相互覆盖。
- 内核进程退出，不等于网络已经恢复到连接前的状态。
- 启动进程成功，不等于 VPN 已经连接成功。
- 自动重连应有最大尝试次数、退避策略、冷却时间和明确的失败原因。
- 关闭 GUI 时，必须定义后台连接是继续运行还是主动断开，不能依赖线程退出时的偶然行为。
- 系统路由和 DNS 变更需要有恢复策略；出现异常时不能无限期留下半失效的网络状态。

建议把自动重连视为一个独立的、可测试的状态机，而不是散落在多个脚本中的循环。

## 5. 第五优先级：把“自主可控”从设计目标变成可验证的安全属性

你的总结反复强调零后门、零遥测、隐私和自主控制。这些目标合理，但“源码在自己手里”不等于“整个软件没有后门”。

还需要审计依赖、构建过程、网络行为、更新机制和运行权限。

特别需要处理：

1. 凭证与配置安全。 Worker 地址、订阅链接、令牌等不应无差别保存在普通 JSON 配置或日志中。需要区分公开配置与秘密配置，并进行必要的脱敏和访问控制。
2. 管理员权限最小化。 不建议为了方便而让整个 GUI 始终以管理员权限运行。优先让普通 GUI 通过受控接口调用需要提权的网络操作。
3. 内核来源与版本固定。 记录内核版本、来源、文件哈希和许可证；升级前运行回归测试。
4. 网络行为审计。 明确哪些域名会被访问、哪些数据会被发送、何时访问以及失败后是否回退到其他服务。
5. 更新与回滚。 更新应可验证来源和完整性，并允许回滚到上一个已知可用版本。
6. 日志隐私。 不仅需要脱敏 Worker URL，也要避免记录完整订阅、代理凭证、私有 IP 信息和其他不必要的敏感内容。

这些工作比在 GUI 上增加更多按钮更能提升项目的长期可靠性。

## 2. GUI 技术：选定一种，不要同时维护两套方案

原文同时提出 PySide6 和 CustomTkinter。我的建议是：

首选 PySide6，作为正式桌面客户端的唯一 GUI 框架。

理由是你的项目需要后台任务、异步状态更新、表格、日志、配置页面和多个功能模块。Qt 的信号槽机制、模型视图体系和成熟的桌面组件适合这类应用。

但 GUI 技术不是最大的风险。无论选择哪种框架，都不能让网络检测、配置生成或拨号过程直接阻塞界面线程。

## 3. 打包方式：不要把“单个 EXE”当成第一阶段目标

你的草案希望将 OpenVPN、Mihomo 和相关文件内嵌进 EXE，同时自动申请管理员权限。

这里建议修改两个地方。

第一，开发阶段使用正常的目录式运行和打包方式。等所有内核都能正确启动、退出、读取配置并恢复网络状态后，再评估单文件打包。单文件模式会增加资源释放路径、内核文件定位、启动时间和故障排查的复杂度。

第二，不要让整个 GUI 默认始终以管理员权限运行。 更合理的设计是普通权限运行界面，将确实需要提权的网络操作放在单独的受控执行路径中。

此外，`APP_ROOT`、`BUNDLE_DIR` 和 `RUNTIME_DIR` 的路径设计需要进一步明确：

- 程序资源目录与可写运行目录必须分开。
- 安装到受保护目录后，不能假设程序目录一定可写。
- 需要定义便携模式、正式安装模式和开发模式各自的数据存储位置。
- 更新程序时不能覆盖用户的历史记录、私有配置和节点缓存。

## 4. 配置管理：当前代码存在需要修正的风险点

第一份文件中的 `LocalConfigManager` 直接将 `WORKER_CHECK_URL`、用户名和密码写入 JSON 配置。代码还会把 `SSTP_USER` 和 `SSTP_PASS` 注入环境变量。

这不一定意味着凭证会立即泄露，但它使秘密信息的存储、传递和日志审计缺少清晰边界。

另外，当前 URL 修正逻辑主要通过字符串判断 `?sstp=`、`@` 和 `/check`。这对于简单输入可能可用，却不适合充当可靠的 URL 验证器。

建议独立重写配置模块，至少做到：

- 使用标准 URL 解析和明确的配置校验规则。
- 区分公开参数、私有凭证与运行时状态。
- 保存前校验，保存后重新读取并验证。
- 写文件采用临时文件与原子替换，避免程序中断时留下半份配置。
- 日志只记录必要的错误类别与脱敏后的上下文。
- 配置错误应明确阻止相关操作，而不是自动猜测并静默修正。

尤其需要注意：原文示例中的 `mask_worker_url()` 只能处理特定形式的 HTTP(S) URL，并不能保证所有日志、异常堆栈和导出文件都已经脱敏。

## 5. 数据过期与黑名单：不能只写注释，必须实现可验证规则

草案里的 `load_eight_groups()` 写有“检查数据是否过期（超过 2 小时告警）”的注释，但展示的代码主要是读取 `updated_at` 并保存到诊断信息，没有看到实际的时间解析和过期判断。

这意味着至少在当前展示的实现中，过期数据告警还不完整。

建议将它改为独立的健康检查：

- 时间字段必须有统一格式与时区规则。
- 时间缺失、解析失败、数据过期和数据来源异常要分别报告。
- 过期数据可以保留用于展示历史情况，但默认不能当作实时可用节点。
- 所有时间阈值应配置化，并由测试覆盖边界情况。

同样，连续五次失败自动永久拉黑节点，也不宜直接作为不可撤销的硬规则。

一次失败可能源于网络波动、远端服务异常或检测器故障，而非节点本身永久失效。建议采用分级处置：

1. 单次失败：记录失败原因。
2. 连续失败：降低排序或暂时隔离。
3. 持续异常：进入冷却期。
4. 多次独立验证仍失败：考虑长期封禁。
5. 手动解除封禁：保留审计记录，并重新检测。

安全底线和质量判断也应分开：明确不合格的 IP 不得进入受保护场景；但检测暂时失败的节点，不应自动等同于已确认的恶意节点。

# 四、评级规则本身也需要一次专项重构

你的四场景规则已经有了具体阈值，这是很好的基础。但目前部分指标可能产生误判。

| 现有设计          | 潜在问题                   | 建议               |
| ------------- | ---------------------- | ---------------- |
| 延迟低于阈值即合格     | 单次测量可能恰好处于网络良好时段       | 结合多次测量、时间跨度与失败率  |
| 抖动使用固定阈值      | 测量方法与采样间隔可能不同          | 统一测量协议和计算方式      |
| 标准差/均值低于 30%  | 均值接近零时比例不稳定，样本太少时结论不可靠 | 设置最小样本量，保留绝对波动指标 |
| 使用节点公布的带宽     | 宣告带宽不等于真实吞吐量           | 区分理论带宽与实测带宽      |
| 根据出口情报判断干净 IP | 情报来源可能不一致或过时           | 保存来源、检测时间和置信度    |
| 连续五次失败即封禁     | 可能把检测器故障当作节点故障         | 区分业务失败与检测系统异常    |

还有一个必须明确的事实：`is_clean=True` 只能表示现有检测规则没有发现指定风险，不能证明一个 IP 绝对干净，更不能保证第三方客服或 AI 平台一定不会风控。

建议将节点状态从简单的布尔值升级为明确的结果，例如：

- `clean`
- `flagged`
- `unknown`

再单独记录证据来源和最后检测时间。这样，未知状态就不会被误当成安全状态。

# 五、测试体系要从“42/42 通过”升级为完整的工程验收

42/42 测试通过是有价值的进展，但测试数量本身不能代表覆盖程度。需要知道这些测试覆盖了什么、哪些场景依然没有验证。

建议把测试分成四层。

单元测试

不依赖真实网络

测试 CSV 解析、评级规则、脏 IP 过滤、未知值处理、配置校验、稳定性计算和八分组结果。

集成测试

验证模块之间的契约

测试 Worker 返回异常、数据字段缺失、JSON 版本不匹配、内核启动失败和配置生成失败。

系统测试

在真实 Windows 环境中测试

验证连接、断开、DNS、系统路由、权限、断线重连、进程退出、休眠恢复和卸载后的网络状态。

安全验收

验证自主可控的实际效果

检查网络访问清单、凭证脱敏、依赖来源、构建产物、权限边界和升级回滚。

建议将以下情况列为发布阻断项：

- 配置无效时仍然开始连接。
- 未知 IP 信誉被当作已确认安全。
- GUI 显示已连接，但实际出口检查失败。
- 断开后仍遗留非预期的路由或 DNS 配置。
- 订阅凭证或私有 Worker 地址出现在公开产物中。
- 更新失败后无法恢复到上一个可用版本。

# 六、哪些地方值得推翻重来？

我把重构分成三个等级，避免为了“架构更漂亮”而浪费已经完成的工作。

| 部分                     | 建议级别    | 具体处理                         |
| ---------------------- | ------- | ---------------------------- |
| `vpngate.py` 的抓取逻辑     | 局部重构    | 保留可验证的抓取与解析逻辑，拆分职责           |
| 四场景评级与八分组              | 专项重构    | 统一数据模型、未知状态和规则引擎             |
| `vpn_dial.py`          | 局部到中度重构 | 保留成熟的拨号逻辑，重新设计生命周期与错误处理      |
| `gen_client_config.py` | 局部重构    | 明确输入输出契约，增加不同内核版本的配置测试       |
| `core_service.py`      | 建议重新设计  | 避免成为同时处理配置、数据、拨号和 GUI 的巨型服务类 |
| `app_gui.py`           | 从零设计新模块 | 只负责界面和交互，不继承旧脚本中的业务耦合        |
| 节点评级与数据契约              | 建议重新设计  | 建立唯一的规范模型与版本化规则              |
| 整个检测平台                 | 不建议推翻   | 现有自动化、Worker 与发布链路仍有复用价值     |
| 整个项目                   | 不建议推翻   | 目前的问题是边界与验证不足，不是所有技术选择都错了    |

特别强调：不要把“重写代码”当作“解决问题”的同义词。

对于已经修复过的九类问题，应该把它们转化为回归测试。否则，重写后很可能重新引入 CSV 跳行、未知抖动被填成零、检测失败被静默忽略、配置凭证错误等旧问题。

# 七、我建议采用的新开发路线

按照风险和依赖关系，我建议这样安排。

## P0

第一阶段：完成现有系统的真实验收

先不增加功能。

- 部署并验证 Worker。
- 验证 A 端配置导入与实际连接。
- 验证 B 端本地 Feed、拨号、出口与断开恢复。
- 将所有失败原因、版本和测试结果记录下来。

完成标准：能够明确说明每一条链路哪些已通过、哪些失败、失败在哪里。

## P1

第二阶段：重构数据与规则引擎

- 定义唯一节点模型和 JSON Schema。
- 统一未知值、过期数据、黑名单和场景资格规则。
- 将旧版 42 项测试转化为回归基线，并补齐关键边界测试。

完成标准：相同输入与规则版本，始终产生可解释、可复现的结果。

## P2

第三阶段：建立统一的连接管理器

- 定义内核适配器接口。
- 实现连接状态机、取消操作、超时和清理。
- 独立管理系统路由、DNS 与连接健康检查。

完成标准：连接管理逻辑不依赖 GUI，也能通过自动化测试验证。

## P3

第四阶段：开发 PySide6 桌面客户端

- 展示八分组和节点详情。
- 提供连接、断开、切换、配置、日志和诊断页面。
- 将所有耗时任务放到后台线程或任务执行层。
- 确保 GUI 关闭、崩溃或重启时，连接状态都有明确处理策略。

完成标准：所有界面操作都调用已测试的服务，而不是直接操作内部数据。

## P4

第五阶段：打包、升级和长期运行

- 固定依赖与内核版本。
- 生成可重复构建的发布包。
- 完成签名或完整性验证、升级回滚、诊断导出和网络恢复测试。
- 最后再考虑跨平台与更多协议。

完成标准：不依赖开发环境，能够安装、运行、更新、诊断和恢复。

# 八、最后一个战略问题：你的目标应该是“完全自主”，还是“完全自己实现”？

这两者并不相同。

你希望摆脱第三方软件的不透明性，但如果连 VPN 内核、协议栈、虚拟网卡驱动、TLS 实现、GUI 框架和更新机制全部自己实现，维护成本和安全风险反而会急剧增加。

我建议采用以下原则：

- 自己掌握的部分： 节点管理、评级规则、连接策略、配置管理、诊断、数据存储、界面与自动化。
- 使用成熟内核的部分： 隧道传输、协议实现、系统代理、必要的虚拟网卡和底层网络处理。
- 严格控制的部分： 第三方依赖来源、版本、网络访问权限、构建产物、升级和回滚。

这样，你可以掌握整个系统的决策权和运行行为，同时避免重复实现已经非常复杂的底层网络技术。

还需要接受一个现实：开源、可审计和可复现构建可以提高可信度，但不能单凭这些属性证明软件绝对没有后门。 真正的自主可控，是能够持续验证、发现问题、修复问题，并知道软件实际做了什么。

## 我的最终建议

当前最值得推进的不是 GUI，而是先完成三个基础成果：

1. 一份经过真实环境验证的现有系统验收报告。
2. 一份统一的节点数据模型与评级规则规范。
3. 一个与 GUI 无关、能够独立测试的连接管理器设计。

这三项完成后，再开发桌面客户端，返工风险会低得多。

如果你现在就要选择一个需要“大改”的地方，我会优先选择节点数据契约与连接生命周期管理，而不是整个项目，也不是已经有一定验证基础的抓取脚本。

它们决定了以后无论增加多少功能、切换多少内核，整个系统能否继续保持一致、可靠和可维护。
