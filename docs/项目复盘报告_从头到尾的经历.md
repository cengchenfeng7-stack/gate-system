## 第一章：起点——为什么要自己搞

### 1.1 最初的需求

一句话：**网络最安全、最稳定、最严格，可以稳定打游戏、稳定下东西、稳定聊国外AI、稳定聊国外客服，拥有最大的包容性。**

拆解成具体目标：
- 四场景通道：⭐客服稳连 / 🎮游戏低延 / ⬇️下载高速 / 🤖国外AI
- 系统级 VPN（不是浏览器插件级）
- 节点质量可验证（不是"看起来能用"）
- 出了问题能修（不是等别人更新）

### 1.2 为什么不用现成的

用户的心声：
> "现在的人都是：使用没问题的时候还好会夸。使用感觉一般了就会考虑换工具。使用感觉很差了不但换工具还进行人身攻击和差评。我要自己开发的话，出了问题修起来也没有怨言，只会说哎呀网络这边没有优化好或者反代没做好或者网关啥的没做好，然后找人帮忙去进行加功能或者进行大改。"

**核心逻辑**：使用第三方软件 = 把网络命脉交给别人。出了问题只能等、只能骂、只能换。自主开发 = 出了问题知道改哪里、知道找谁帮忙、知道怎么修。

## 第二章：架构设计——三块 + 双客户端

### 2.1 三块架构

```
前端/调度（GitHub Actions，每 30 分钟）
    ↓
后端/检测（Cloudflare Worker，SSTP over TLS + PPP + 出口情报）
    ↓
客户端（A 端 mihomo/Clash + B 端 OpenVPN）
```

**为什么这么分**：
- 前端放 GitHub Actions：免费、定时、有版本管理、有日志
- 后端放 CF Worker：全球边缘节点、出口 IP 多样、免费额度够用
- 客户端双路径：A 端走 VLESS（低延迟、灵活分流），B 端走 OpenVPN（系统级、全局代理）

### 2.2 为什么检测用 SSTP

VPN Gate 官方提供三种协议：OpenVPN / L2TP/IPsec / SSTP。

选 SSTP 的原因：
- Windows 原生支持（不需要额外客户端）
- 走 TCP 443（HTTPS 端口，穿透性强）
- 可验真出口 IP（不是 ping 通了就算通）

**但 SSTP 的代价**：延迟天生高（2000-9000ms），不适合游戏/客服。

### 2.3 四场景判定标准

| 场景 | 核心指标 | 阈值 |
|---|---|---|
| ⭐客服稳连 | 干净 IP + 住宅 + 长在线 + 低抖动 + 低延迟 | is_clean=True, residential, uptime≥12h, jitter≤150ms, lat≤600ms |
| 🎮游戏低延 | 延迟 + 抖动 + 负载 | lat≤400ms, jitter≤100ms, sessions≤250 |
| ⬇️下载高速 | 账面带宽 + 稳定性 | speed≥2Mbps + 波动率<30% |
| 🤖国外AI | 干净 IP + 长在线 + 低抖动 + 低延迟 | is_clean=True, uptime≥6h, jitter≤200ms, lat≤800ms |

**铁律**：脏 IP（is_abuser/is_tor/is_bogon）永远进不了客服/游戏/AI 通道，pin 也不能覆盖。

## 第三章：前端开发——vpngate.py 的 1048 行

### 3.1 核心流程

1. **抓取 feed**：官方 API（`vpngate.net/api/iphone/`）+ 镜像回退
2. **筛选 SSTP 节点**：从 .ovpn 配置提取 `proto tcp` + `remote <host> <port>`
3. **入口域名自检**：TCP/TLS 握手验证优选入口域名
4. **送检**：调 checker Worker 的 `/check?sstp=host:port`
5. **二次复测**：每国前 N 名做第 2 次防闪断复测
6. **评级**：四场景判定 + 综合分排序 + 分层
7. **发布**：生成 data.json + 八分组节点列表 → GitHub Pages

### 3.2 9 个关键修复（R1-R9）

| 编号 | 问题 | 修复 |
|---|---|---|
| R1 | parse_csv 跳行 | 不跳行、不抬门槛、缺列安全默认 |
| R2 | 历史缓存兜底 | 彻底移除，无成功不发布 |
| R3 | 检测会话重试 | 零重试，429/5xx 直接判 Worker 异常 |
| R4 | 复测不分原因 | 区分业务失败（淘汰）/ Worker 抖动（保留） |
| R5 | 无超时保护 | cron30 + 超时 25 分钟 + cancel-in-progress |
| R6 | jitter 冒充 0 | 未复测 = None（未知），uptime=0 = 未知 |
| R7 | 入口全失败静默 | 返回完整列表 + 明确告警 |
| R8 | 硬编码 Worker 地址 | 删除，靠 Secret，未配置直接失败 |
| R9 | 凭证写死 | 统一用 SSTP_USER/SSTP_PASS |

### 3.3 四场景评级的演进

**v1（初版）**：只看延迟和带宽 → 脏 IP 混入客服通道
**v2（加脏 IP 过滤）**：is_clean 判定 → 但 checker 不返回 is_clean
**v3（加历史缓存）**：累积节点 → 死节点冒充稳连（R2 修复）
**v4（最终版）**：历史缓存 + 自动黑名单 + 养鱼池 + 稳定性判定

## 第四章：后端检测——checker Worker 的重生

### 4.1 上游基线：cm-Workers-CheckSocks5

社区项目，8034 行，支持 SOCKS5/HTTP/HTTPS/TURN/SSTP 五协议检测。

**核心能力**：
- SSTP over TLS + PPP 拨号 + TCP-over-PPP 状态机
- 出口 IP 情报查询（iplocate.io）
- 多协议检测

**问题**：
- 面板有第三方埋点（tongji.090227.xyz）
- ECH 配置嵌入节点链接（导致客户端报错）
- 无 TOKEN 鉴权（任何人可白嫖）

### 4.2 hardened 版的 7 处改动

| 改动 | 说明 |
|---|---|
| 删除面板埋点 | 去掉 tongji.090227.xyz 统计脚本 |
| 新增 TOKEN 鉴权 | /check 接口可设访问密码 |
| 出口字段补全 | +country/country_code/city/continent/is_clean |
| DoH 双端点 | cloudflare → dns.google 回退 + 5 分钟缓存 |
| 超时收紧 | 12000/9999/8000 → 10000/6500/6500 |
| 面板替换 | 中性备案文案 + 新面板 |
| 去 BOM | 删除文件头 BOM |

**关键结论**：hardened 的 SSTP 代码和上游逐字节相同，没动一行传输逻辑。

### 4.3 81/81 全败的根因

**症状**：Worker 返回 200、worker_error=0、6.3 秒内全部业务失败。

**排查过程**：
1. 对比本地版本 → 上游 ≡ 修改后（字节级相同）
2. 对比 hardened → 只差 7 处（见上）
3. 查看 Pages data.json → 昨天 16/83 成功
4. 对比昨天和今天 → 唯一变量：Actions secret 被改

**真凶**：GitHub Secret `CHECK_WORKER` 的 `?sstp=` 后**少了 `vpn:vpn@`**。

前端拼接 `WORKER_CHECK_URL + host:port`，如果 secret 是 `.../check?sstp=vpn:vpn@`，拼出来就是 `.../check?sstp=vpn:vpn@vpn2070.opengw.net:5555`（有凭证）。如果 secret 是 `.../check?sstp=`，拼出来就是 `.../check?sstp=vpn2070.opengw.net:5555`（无凭证）。

无凭证 → SSTP 服务器要求 PAP 认证 → worker 报 `SSTP server requires PAP authentication` → 每个节点 ~1.4s 快速失败 → 81 节点并发 16 → 总耗时 ~5-13s。

**修复**：secret 改回 `https://<worker>.workers.dev/check?sstp=vpn:vpn@`。

## 第五章：ECH 兼容性——协议更新的代价

### 5.1 问题复现

worker 开启 ECH 后：
- Clash 订阅 ✅ 能用
- SingBox 订阅 ✅ 能用
- 节点链接/自适应/Base64 ❌ 报错 `[V2rayParser] invalid sing-box config: parse outbound[muchen] error: invalid ECH configs pem`

### 5.2 根因

edgetunnel 代码把 ECH 配置塞进两个地方：
1. **节点链接的 URL 查询参数**：`&ech=...` → 旧版 sing-box 不认识
2. **SingBox 配置的 TLS 字段**：`query_server_name: cloudflare-ech.com` → 需要 sing-box 1.13.0+

`query_server_name` 是 sing-box **1.13.0+** 的新字段，Hiddify 当前版本的 sing-box 太旧不认识，解析到就报 `invalid ECH configs pem`。

### 5.3 认知纠偏

| 错误认知 | 正确理解 |
|---|---|
| "ECH 是代理协议" | ECH 是 TLS 扩展，在 TLS 握手阶段工作 |
| "ECH 和代理冲突" | ECH 在 TLS 层，代理在应用层，互不干扰 |
| "关闭 ECH 安全下降一大截" | ECH 只藏 SNI，代理流量本身还是端到端加密的 |

**ECH 的正确工作方式**：
1. 客户端连接服务器（TLS 握手）
2. 客户端通过 DNS HTTPS 记录获取 ECH 配置
3. 客户端用 ECH 配置加密 Client Hello 中的 SNI
4. 服务器解密 SNI，继续 TLS 握手

**不需要在节点链接或订阅配置里显式嵌入 ECH 字段**。

### 5.4 最终方案

| 格式 | ECH 处理 | 结果 |
|---|---|---|
| 节点链接（vless://） | 恢复 ech 参数 | 新版客户端识别 |
| Clash 订阅 | ech-opts 标准格式 | Clash Verge Rev 支持 |
| SingBox 订阅 | 不带 ech 字段 | 旧版 sing-box 不报错 |
| 所有格式 | ECH 通过 DNS HTTPS 记录自动获取 | 全协议兼容 |

### 5.5 教训

**协议兼容性是 VPN 系统的核心挑战**：
- ECH 等新技术采用速度快，但客户端/服务端/转换层支持时间差大
- 显式嵌入新字段会导致旧客户端报错
- 最佳实践：让新特性通过标准机制（如 DNS HTTPS 记录）自动工作，不显式嵌入

## 第七章：B 端双模式 feed

### 7.1 问题

vpn_dial.py 拉 feed 时，官方 API 和镜像都连不上（网络封锁）。

### 7.2 解决方案

**双模式：本地为主，在线为辅**

```
本地 feed.csv 存在？ → 是 → 从本地读取（零网络依赖）
                ↓ 否
        尝试在线拉取（官方 + 镜像）
                ↓ 成功
        保存到本地缓存
                ↓ 失败
        用本地缓存（如果有）
                ↓ 都没有
        die("feed 获取失败")
```

### 7.3 使用方法

```powershell
# 主模式：本地 feed（零网络依赖）
python vpn_dial.py --feed-file feed.csv --scene support

# 辅模式：在线拉取（自动保存到 feed.csv）
python vpn_dial.py --refresh --scene support

# 不指定 --feed-file 也行，默认找 feed.csv
python vpn_dial.py --scene support
```

## 第九章：血泪坑清单（10 条）

### 坑 1：检测全失败（81/81）
**症状**：Worker 返回 200 且 worker_error=0、6.3 秒内全部业务失败。
**根因**：GitHub Secret `CHECK_WORKER` 的 `?sstp=` 后少了 `vpn:vpn@` 凭证。
**修复**：secret 改回 `.../check?sstp=vpn:vpn@`。
**教训**：前端拼接 URL 时，secret 格式必须和 worker 参数解析方式匹配。

### 坑 2：worker 半死不活
**症状**：根路径返回 nginx 页（活着），但 /login 超时、/sub 重置。
**根因**：edgetunnel 代码的 ECH 嵌入方式导致客户端解析报错。
**修复**：不在节点链接里显式嵌入 ech 参数。
**教训**：显式嵌入新字段会导致旧客户端报错。

### 坑 3：自定义域 1016
**症状**：访问自定义域返回 1016 Origin DNS error。
**根因**：自定义域没真正挂到 worker（只在 zone 里存在）。
**修复**：worker → 域 → 添加自定义域。
**教训**：CF 的"域"和"自定义域"是两回事。

### 坑 4：本地两个流水线副本不一致
**症状**：`能跑版` 和 `gate` 目录内容哈希不同。
**根因**：开发过程中只更新了一处。
**修复**：统一到 `能跑版`，另一处删除。
**教训**：多副本 = 灾难。只维护一份源码。

### 坑 5：Compare-Object 行级 diff 误导
**症状**：diff 出几百行"差异"，实际只是对齐噪声。
**根因**：Compare-Object 在 HTML 块不同的两个文件上产生大量错位噪声。
**修复**：用函数级 diff（按函数名提取全文比对）。
**教训**：大文件 diff 不要用 Compare-Object 的行级结果做判断依据。

### 坑 6：PowerShell 中文路径乱码
**症状**：`Get-ChildItem 'F:\稀奇玩意\能跑版'` 找不到路径。
**根因**：磁盘目录名是双重重编码，`-like` 匹配失败。
**修复**：直接指定中文路径作为参数（`Get-ChildItem 'F:\稀奇玩意\能跑版'`）可以工作。
**教训**：规则 6 存在的原因。用动态路径或直接字面量。

### 坑 7：CF Worker 面板有第三方埋点
**症状**：旧版 checker 面板每次被打开就向 tongji.090227.xyz 汇报 worker 域名。
**根因**：cmliu 上游代码内嵌的访问统计脚本。
**修复**：hardened 版已移除。
**教训**：公开 worker 的面板代码要审计，第三方埋点会泄露私有域名。

### 坑 8：GitHub Actions 日志只打计数，不打 error
**症状**：检测失败时只知道"失败 80"，不知道各死在哪。
**根因**：vpngate.py 的 build_outputs 只持久化 success 节点，error 被丢弃。
**修复**：加失败原因聚合（ERROR SUMMARY）。
**教训**：规则 2（失败不静默）的体现。错误信息必须落盘/打日志。

### 坑 9：.github 文件夹上传丢点号
**症状**：通过某些方式上传 .github 文件夹，点号丢失。
**修复**：用 GitHub 网页 Create new file 手打路径 `.github/workflows/check.yml`。
**教训**：规则 7 存在的原因。

### 坑 10：变量顺序错误（UnboundLocalError）
**症状**：`NameError: name 'data' is not defined` 或 `UnboundLocalError: cannot access local variable 'watch_nodes'`。
**根因**：在函数内引用变量之前没有赋值。
**修复**：把变量定义移到使用之前。
**教训**：Python 函数作用域规则——变量必须先定义后使用。

## 第十一章：核心教训

1. **自主可控 > 依赖他人**——出了问题有明确的修复路径，不需要等待、不需要抱怨、不需要信任他人。

2. **协议兼容性是 VPN 系统的核心挑战**——新协议特性（ECH）的采用速度不一，客户端/服务端/转换层支持时间差大。最佳实践：让新特性通过标准机制自动工作，不显式嵌入配置。

3. **失败不静默**——错误信息必须落盘/打日志。只打计数不打 error 的日志等于没有日志。

4. **多副本 = 灾难**——只维护一份源码，其他用符号链接或删除。

5. **改动必过测试**——任何代码改动必须过离线测试/语法校验，不允许"看起来对"就交付。

6. **历史缓存是双刃剑**——能扩大节点池，但也能让死节点冒充稳连。必须有自动淘汰机制。

## 结语

这套系统从"用别人的软件"到"自己造轮子"，经历了：
- 前端从 0 到 1048 行
- 后端从上游基线到 hardened 版
- 面板从四分组到八分组
- B 端从单模式到双模式 feed
- 仓库从旧到新迁移

**核心驱动力**：对"使用别人软件"的不信任，对"自主可控"的追求。

**一句话总结**：用别人的软件，出了问题只能抱怨；自己开发，出了问题只会想办法修——这就是自主开发的价值。
