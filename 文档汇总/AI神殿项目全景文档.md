## 二、对话历程回顾

### 阶段一：7 项需求技术审查（起点）

用户提出 7 项重构需求，核心痛点：

1. 40+ 提供商配置不能塞 `.env`（深层 JSON 会撑爆扁平结构）
2. 工作流容易退化成单 AI（状态未独占）
3. 知识库无法存储
4. 群成员进不去、新建智能体找不到
5. 1v1 私聊缺失
6. 上下文“强制切片 15-20 条”会触发 tool_calls 失配 400
7. 权限三档被窄化为“改 .env 的权限”

结论：四个致命缺陷成立，采纳「解耦持久化 + Tool-Pair Preserving + Tool Interceptor 三档 + Session 级状态机」路线。

### 阶段二：排查“改动是否成功”——发现幻觉

用户实测“什么都没改”。排查确认：

- `tools.mjs` 损坏至 13MB（同一代码块重复数百次）
- `providers.json` 存在但未接入聊天管线
- 前端未更新；工作流/私聊/心跳/截断只有数据库字段，没有逻辑

### 阶段三：全面修复

重写 tools.mjs（13MB → 465 行）+ 工作流状态机、私聊路由、SSE 心跳、工具成对截断 + 9 模式前端。

### 阶段四：后台管理“消失”危机

新前端覆盖了原 React 应用，导致知识库/模型/智能体管理入口消失。方案：保留清爽主界面 + 独立 `admin.html` 后台。

### 阶段五：AI 神殿扩建设计 + 第一阶段实施

设计 6 种扩展模式 + 自主性四级模型；实施数据库新表、4 大引擎（主动服务 / 持续对话 / 层次记忆 / 自主学习）、6 模式路由、9 模式前端。

### 阶段六：AI 提供商“真修”

实测发现 3 个隐蔽 bug + 7 个 Key 体检，最终切换到 SiliconFlow 端到端成功。

### 阶段七：真实性与可观测性攻坚（本轮）

- 修复“表演型执行”“整理空气”“工作流假执行”
- 补齐提示词/智力/审计/Token/知识库/商店/图谱/MCP/沙箱/插件/断点续跑
- 接通 GUI 工具与默认工作区

### 3.9 大步 13：工作流真实化 + 主动服务修正 + GUI + 工作区 ✅

#### 13.1 工作流：从假执行改为真执行

**问题**：

- `runWorkflow` 的阶段全是占位函数，直接返回 `分析: 输入 / 执行: 输入 / 总结: 输入`，从未调用模型。
- 自定义模板阶段只返回 `完成阶段「x」`。
- SSE 写成 `{ type:"workflow_progress", ...progress }`，`progress.type` 覆盖外层 `type`，前端收不到阶段事件，只显示“初始化 / 执行完成”。

**修复**：

- 每个阶段通过 `runDirectTurn` 真实调用模型 + 工具，流式输出文本。
- 阶段结果注入下一阶段提示词。
- 默认流：分析 → 执行 → 总结；另有代码审查、文件操作、自定义模板。
- SSE 保留外层 `type`，阶段事件放 `event` 字段；前端按 `event` 渲染。
- 阶段失败不阻断后续阶段。

**实测**：输入“在工作区创建 hello_workflow.txt，内容写 workflow-ok” → 3 个阶段真实执行，`write_file` 落盘，文件内容 `workflow-ok`。

#### 13.2 主动服务：能力边界修正

**更正**：之前把 `snake.html` 归因于主动服务是**错误的**。经用户指正，它由**持续对话**模式产出。

当前主动服务的真实行为：

- 用户发消息时，主动服务引擎先做规则分析（相似问题、未完成任务、知识库缺口），有结果就下发建议卡片。
- 随后走真实群聊流程（模型 + 工具），因此工具调用是真实的。
- 但它**不是后台常驻巡检**：没有消息/没有轮询就不分析；没有定时任务与跨会话画像。

**本轮改进**：结束时下发 `proactive_summary`，显示本轮真实工具调用次数与建议内容，避免“看不出来做了什么”。

**结论**：主动服务不是“假执行”，但“主动性”只到 L2 的一半，离“自动发现问题”还有距离。

- **实测**：忽略一条建议后，接口返回 `feedback: dismissed`，状态变为 `dismissed`。

#### 14.5 L3：任务队列 + 后台调度 + 重启恢复

- `TaskQueueService` 每 30 秒领取 `queued` 任务，后台复用自主代理真实执行链路（规划 → 工具执行 → 验证 → 学习 → 进化）。
- 后台执行使用空事件 sink，不依赖 HTTP 连接；完成后回写一条会话消息，失败/暂停写入建议卡片。
- 服务启动时把残留 `running` 任务改回 `queued`，按检查点自动续跑；暂停任务可在 10 分钟后自动重试（最多 2 次）。
- 后台页支持入队、优先级、重试、放弃、进度与重规划次数展示。
- **实测**：入队「创建 l3_queue_test.txt」→ 自动规划 2 步 → 真实落盘 `queue-ok` → 任务 `completed` 100%。

#### 14.6 L3：失败重规划

- 步骤异常后，把「总目标 + 已完成步骤 + 失败原因 + 原剩余计划」交给模型重写剩余 1～3 步。
- 每任务最多 2 次；模型未返回有效计划时兜底为「换一种方式重试」。
- 重规划结果写回 `plan` / `total_steps` / `replan_count`，前端显示「失败重规划」事件。
- **实测**（临时失败钩子）：第 1 步强制失败 → 自动重规划出 2 个新步骤 → 文件仍成功落盘 → `replanCount=1`，任务完成。验证后已移除测试钩子。

#### 14.7 L3：策略沉淀与复用

- 任务完成且「≥2 步、平均评分 ≥0.8」时，把执行计划沉淀到 `strategy_library`（关键词 + 步骤 + 均分）。
- 新任务规划前按关键词相似度匹配最多 2 条高分策略注入规划提示词，并累计使用次数。
- **实测**：首个任务均分 0.8 自动生成策略；第二个同类任务命中该策略（使用次数 +1）。

#### 14.8 L3：长程目标管理与验收

- `agent_goals` 支持标题、描述、验收标准、截止时间、优先级、进度；任务可通过 `goal_id` 关联目标。
- 任务完成自动回算进度；有验收标准时由模型判定 `passed/reason/progress`，通过则目标置为 `completed`。
- 巡检会对 24 小时内到期或已逾期目标生成提醒建议。
- **实测**：目标「验证 L3 长程目标闭环」+ 关联任务 → 任务完成后自动验收通过，目标状态 `completed`，理由「文件已创建且内容为 goal-ok」。

#### 14.9 前端

- 后台新增「♾️ 自主性 L2/L3」页：巡检状态/配置、用户画像、任务队列、策略库、长程目标。
- 主界面：建议「忽略」上报 dismissed；任务栏显示排队任务与重规划次数；每 60 秒轮询建议与任务。
- **实测**：浏览器验证后台 6 个区块全部渲染、立即巡检生效；主界面 9 模式正常、无 JS 报错、906px 无横向溢出。

## 九、排错方法论

1. **信实证不信宣称**：每次“改好了”必须过真实请求验证，不接受静态检查通过。
2. **怀疑环境优先**：配置类问题先查外部环境是否覆盖（#6 就是环境变量覆盖）。
3. **用 node 测 API**：PowerShell 的 `Invoke-RestMethod` 有编码与错误体丢失问题。
4. **Key 失效是常态**：定期体检比加日志更重要。
5. **UI 看不到不等于没执行**：查审计日志 + 数据库，再判断真假（主动服务即此例）。
6. **归因要留证据**：mode、session、agent 必须一起看；#42 证明只看消息内容会归错模式。
